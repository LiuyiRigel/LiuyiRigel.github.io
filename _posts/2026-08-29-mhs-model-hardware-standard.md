2026 年 8 月 27 日，Anthropic 宣布开放 **Model Hardware Standard（MHS，模型硬件标准）** 的研究预览版——一个让 AI Agent 安全发现、连接并操作物理设备的共享规范。媒体普遍把它称为"**物理世界的 MCP**"。

这篇技术报告从个人开发者的角度，把 MHS 讲明白：它解决什么问题、怎么工作、怎么用、历史脉络、能用到哪里、以及它对独立开发者意味着什么。

---

## 1. TL;DR

- **MHS 是什么**：一套标准化"驱动程序"规范，让 AI Agent 能跨网络发现并操作显微镜、液体处理仪、机械臂等物理设备。
- **解决什么**：传统实验室/工厂集成硬件需要数周甚至数月，MHS 把它压缩到几小时甚至几分钟。
- **谁做的**：Anthropic 与 **HHMI Janelia Research Campus** 合作开发，Anthropic 主导。
- **现状**：研究预览版（需申请），面向科研实验室和先进制造商；计划在安全评估后**开源**。
- **三种控制路径**：MCP、命令行（CLI）、代码文件（API）。
- **关键设计**：设备特性用**自然语言标签**描述，自动生成"参考文件"（reference file）供 Agent 读取。
- **对个人开发者**：模型无关、协议标准，任何 Agent 框架都能用；现阶段是关注与准备的窗口期。

---

## 2. 背景：为什么需要"硬件版 MCP"？

### 2.1 物理设备的"巴别塔"问题

过去两年，AI Agent 在**软件世界**里突飞猛进——它们能调用 API、操作浏览器、读写文件。软件工具有一个前提：**它们都有 API**。MCP（Model Context Protocol）正是统一了"Agent 访问外部数据和工具"的接口。

但**物理世界完全是另一回事**：

- 一台显微镜说一种协议；
- 一台移液机器人说另一种；
- 读板机可能**什么协议都不说**，只有屏幕和按钮；
- 机械臂的重量、泵的安全速度上限，这些关键信息**不在代码里**，而在纸质手册、某人的电脑里、或者干脆是"老师傅的经验"。

要把三台这样的设备凑在一起协同工作，就是一次**定制软件项目**——通常耗时数周甚至数月，且每次换设备都要重来。

### 2.2 MHS 的切入点

Anthropic 的思路不是去造硬件（它没有收购 Physical Intelligence，也没有自建硬件实验室），而是**构建硬件之上的软件层**——"不卖硬件，而是做所有人都要插的插座"。

> MHS 瞄准的是**设备抽象层（device abstraction layer）**：它不是机器人的大脑，而是大脑通往真实设备的**路径**。

这也解释了它的定位：NVIDIA 的 GR00T、Physical Intelligence 的 π0 这类"机器人基础模型"是 MHS 的**潜在使用者**，而不是竞争者。

---

## 3. MHS 怎么工作：四块核心拼图

### 3.1 标准化驱动（Standardized Driver）

MHS 的核心是一个**标准化驱动程序**——运行在计算机与硬件设备之间的软件。每个 MHS 驱动都暴露同一套**极简原语（primitives）**：

| 原语 | 含义 | 例子 |
|---|---|---|
| `read` | 从设备读取状态 | `get temperature`（获取温度） |
| `write` | 向设备写入指令 | `set temperature`（设定温度） |

任何带可编程接口的设备都能理解并执行这套原语。同时，每个设备以**标准格式宣告自己**，让 Agent 和设备能跨网络互相发现——不再需要逐个编写"翻译器"。

### 3.2 自然语言标签（Tags）：把"老师傅的经验"写下来

这是 MHS 最有意思的部分。物理设备有许多**代码表达不出来的特性**：

- 机械臂有多重（关系到如何安全操作它）；
- 泵最高能安全跑多快；
- 哪些操作是危险的。

过去这些信息散落在纸质手册、个人电脑或隐性知识里。MHS 让用户**直接用自然语言**把这些事实写成标签（tags）——既可以自己写，也可以**和 Agent 对话，让 AI 采访你**关于硬件设置的情况。

### 3.3 参考文件（Reference File）：设备的"营养标签"

基于标签，MHS 驱动会自动生成一份**参考文件**，描述设备：

- 能测量什么；
- 能调整什么；
- 将强制执行哪些安全限制。

> 可以把它想象成"贴在每台机器上的营养标签"：写一次，任何 Agent 都能读。

有了参考文件，Agent 面对**从未见过的设备**也知道怎么用——这是 MHS 与"为每台设备写死代码"的本质区别。

### 3.4 三种控制路径

设备连接并描述完成后，Agent 有三种方式控制硬件，三者协同可实现**一行代码协调多台设备**：

1. **MCP**：通过标准协议接入 Agent harness；
2. **命令行（CLI）**：直接操作设备；
3. **代码文件（APIs）**：把驱动命令编排成可复用的程序。

**代码文件尤其关键**：当任务太长、或需要比 Agent 在线推理更快的速度时，Agent 可以把多台设备的驱动命令串联成代码文件，让设备**自主执行**，无需每一步都经过模型推理。

> 官方观察到：Claude 调整激光 → 通过摄像头观察光束如何移动 → 重复摸索理解事件序列 → 然后把学到的流程**打包成确定性脚本**，整个校准过程变成一条命令运行——不再需要逐步推理。

## 4. 一个完整例子：QuEra 的量子激光校准

QuEra（用中性原子造量子计算机的公司）用 MHS 让 Agent 控制量子机内部激光系统的组件。Agent 开发的控制器能在**无人工干预**的情况下恢复激光"锁定"（激光与原子交互必须保持的超精密频率），**恢复成功率 99.3%**。

这个例子展示了 MHS 的完整闭环：Agent 读设备状态 → 推理 → 微调 → 观察反馈 → 再调整 → 最终沉淀为自动化脚本。

## 5. 历史脉络：从 MCP 到 MHS

MHS 不是凭空出现的，它几乎是 **MCP 成功路径的复制**：

| 时间 | 事件 |
|---|---|
| 2024-11 | Anthropic 发布 **MCP**，标准化 AI 访问外部数据和工具 |
| 2025-03 | OpenAI 采纳 MCP |
| 2025 年中 | Google DeepMind、Microsoft 跟进 |
| 2025-12 | Anthropic 将 MCP 捐赠给 Linux 基金会旗下的 **Agentic AI Foundation**，Google、Microsoft、AWS 成为支持成员 |
| 至今 | MCP 约 9700 万月 SDK 下载量、约 1 万个活跃服务器 |
| **2026-08-27** | **MHS** 研究预览发布 |

MHS 继承了 MCP 的设计意图：**模型无关**（不是 Claude 专属）、任何 Agent harness 都能通过标准协议（如 MCP）访问、并明确计划**开源**。

> 让竞争对手容易采用看似"让步"，但这正是 MCP 成为标准的方式：**不卖硬件，而是造一个所有人都必须插入的插座**。

一个值得注意的差异：MCP 能快速成为标准，是因为"AI 访问软件工具"这个位置**基本是空的**。而 MHS 所在的设备抽象层**并不空**——它要和 SiLA 2、OPC UA/LADS、ROS 2、Modbus/PLC 等现有标准竞争（详见 §7）。

## 6. 适用范围：能做什么，不能做什么

### 6.1 适用场景（现在就能做）

- **科研实验室自动化**：药物发现实验（BCA 蛋白测定）、qPCR 监控、剂量反应实验；
- **显微镜编排**：统一多厂商显微镜 rig（如 HHMI Janelia 把原本分散在 7 个厂商程序里的设备统一起来）；
- **先进制造**：机械臂操作、多机器人协同、质量检测；
- **量子硬件**：激光校准、频率锁定；
- **任何"有可编程接口"的设备**——这是 MHS 的硬性前提。

### 6.2 明确不能做 / 尚未支持

- **无编程接口的硬件**：暂不支持，Anthropic 正与厂商合作开发驱动；
- **物理直觉**：Claude 主要通过文本和图像学习物理世界，**空间与物理推理仍需专家监督**。例如 Genentech 实验中，研究人员必须引导 Claude 认识到"样品起泡"是物理故障而非软件错误；
- **安全责任**：MHS 的预览阶段明确需要人类专家监督，尚未达到完全自主的安全标准。

### 6.3 与现有标准的对比

| 标准 | 领域 | 定位 | 与 MHS 的关系 |
|---|---|---|---|
| **SiLA 2** | 实验室自动化 | 基于 Web 技术，IT 团队易上手 | 竞争者（机器对机器） |
| **OPC UA / LADS** | 过程工业 | 工业自动化，实验室设备扩展 | 竞争者 |
| **ROS 2** | 机器人 | 事实标准中间件 | 竞争者/共存 |
| **Modbus / PLC** | 传统工业 | 老协议，常与新型设备混用 | 存量兼容问题 |
| **MHS** | 设备抽象层 | **为 LLM Agent 设计** | 差异化：自然语言标签 + 参考文件 |

**关键差异**：SiLA 2 和 OPC UA 是为"机器对机器"设计的；而"用自然语言写下机械臂重量、哪些操作危险，让一个从没见过这台设备的 Agent 读懂"——**现有标准都不做这件事**。这是 MHS 真正的空白地带。

## 8. 从个人开发者角度：这意味着什么？

### 8.1 现在你能做什么

- **申请研究预览**：官方开放了申请入口（modelhardwarestandard.com），面向科研实验室和先进制造商。个人研究者如果有实验室合作渠道，可以申请；
- **熟悉 MCP**：MHS 通过 MCP 接入，把 MCP 生态玩熟 = 为 MHS 打好基础；
- **关注开源**：Anthropic 明确计划开源。**开源之日就是个人开发者的入场券**——届时可以给自家设备写 MHS 驱动。

### 8.2 对个人开发者的机会

1. **设备驱动是新的"插件经济"**：MCP 时代个人开发者写"服务器/插件"赚到了生态红利；MHS 时代，**写设备驱动**可能就是下一个类似机会——尤其针对现有厂商不覆盖的冷门设备；
2. **低门槛差异化**：MHS 的标签机制让"设备适配"从写代码降维到"写自然语言描述"，个人开发者可以专注在**某个垂直设备品类**上做深度适配；
3. **Raspberry Pi 入场**：树莓派多款产品支持 MHS，意味着**个人硬件项目**（DIY 机械臂、传感器台架、家庭实验室）可以直接接入 Agent——这是个人开发者最现实的切入点；
4. **标准未定，先占位**：设备抽象层还没有赢家，谁先给流行设备写好驱动、做好文档，谁就在标准扩散时占据生态位。

### 8.3 需要警惕的

- **标准的"锁定"风险**：谁制定规范，谁就决定"什么算安全限制、哪些设备优先支持"。个人开发者依赖 Anthropic 主导的标准，存在长期依赖问题；
- **安全责任**：让 AI 操作能"压断手"的机械，安全边界必须由接口层强制，而不是指望模型自觉。个人项目尤其要遵守物理安全红线；
- **预览期不完整**：目前只是研究预览，正式安全评估与"物理安全路线图"还没发布，不宜在真实产线/危险设备上依赖它。

### 8.4 一个务实的建议路线

```
第 1 步：吃透 MCP（Agent 接软件的接口）
第 2 步：关注 MHS 开源与安全评估进展
第 3 步：选一个"有可编程接口"的小设备（如树莓派 + 步进电机/传感器）
第 4 步：用 MHS 思路给它写驱动 + 自然语言标签 + 参考文件
第 5 步：发布为开源驱动，切入垂直生态位
```

---

## 9. 展望与争议

MHS 能否成为物理世界的"通用接口"，取决于**分发而非规范质量**——即设备厂商是否默认搭载。Anthropic 已经用 MCP 证明过一次这条路径（开放 → 被采纳 → 捐赠基金会 → 成为事实标准）。但设备抽象层不是空地：SiLA 2、OPC UA、ROS 2 已经深耕多年，MHS 需要证明"为 LLM 设计"的差异化足够强。

另一个值得思考的问题：**当定义标准的一方同时定义安全标准**，这个安全线该由谁、如何设定？这是 MHS 从预览走向正式标准前，社区必须回答的问题。
